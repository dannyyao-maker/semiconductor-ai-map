# /新事件

把「世界上剛發生的重大事」變成一個可以玩的事件任務（狀況簡報 → 地圖導覽 → 影響矩陣 → 3 題）。
來源清單在 `data/event-sources.json`（`enabled: true` 才會檢查）。

**這個指令的設計目標：使用者沒有時間逐件確認，所以由你自己查證、自己決定能不能上線。** 因此「自動檢查」是最後一道防線，寫事件時要比平常更保守。

使用者指定的範圍：$ARGUMENTS

## 鐵則（不能違反）

1. **數字只用原文裡有的。** 事件裡每個數字都要在引用的原始文件找得到；自己推算的要寫進 `derived`（並寫 `at` 位置）。檢查工具會擋下找不到的數字，**不要想辦法繞過檢查**，找不到就改文字或刪掉。
2. **可信來源的標準不用太高，但要能對照原文。** 官方資料（SEC 申報、法說會、政府公告）一個來源就夠；常被其他企業和媒體當作公開資料引用的二手來源（研究機構如 TrendForce、主流財經科技媒體）也可以，但要有**兩個以上獨立的發布者**、原文抓得到、數字對得上。**傳聞不是事實**：標題或內文是「據傳」「消息人士」「未經證實」的消息，不要做；除非有官方確認。
3. **只講商業面。** 角色、營收、毛利、需求、議價、產能、政策影響；不寫製程、規格細節；不寫買賣建議、目標價。
4. **用自己的話改寫**，不照抄原文長句；專有名詞附英文；繁體中文；台灣讀者看得懂。
5. **每次最多處理 `rules.maxEventsPerRun` 個事件**（預設 2），超過的列出來給使用者選。

## 第 1 步：找新文件

```bash
node tools/watch-sources.mjs $ARGUMENTS
```

會列出新文件並存到 `inbox/new-items.json`，同時更新 `tools/watch-state.json`（記錄「已看過」，同一份不會重複處理；這個檔案要一起 commit）。想先看看而不記錄，加 `--dry`。

## 第 2 步：挑出「重大」的

不是每份文件都要做成事件。**值得做**的：

- 追蹤公司的季報／法說會（營收、毛利、財測、資本支出有明顯變化或和預期不同）
- 資本支出、產能、擴廠的重大宣布
- 出口管制等政府規則的變動（影響 AI 晶片、設備、代工）
- 影響整條產業鏈、至少牽動 3 個環節的事

**不要做**：董事會例行決議、股利公告、沒有新資訊的月營收（除非創高、或季增減超過 15%）、同一件事的重複報導、只有封面沒有內容的申報。

**政府公告要特別小心**：法規本文通常只寫日期和條文，不會說對誰有利或不利。如果來源本身沒有說明商業影響，就**不能**靠自己的知識補上影響（那些句子沒有來源）；要嘛找到官方的說明文件（例如 BIS 新聞稿、聯邦公報的前言摘要）一起引用，要嘛這件事就跳過，並在回報裡寫「來源只有條文，沒有影響說明」。

挑完先把「要做哪幾個、為什麼」用一兩句話列給使用者（本機手動執行時要等確認；在排程裡執行時直接做）。如果沒有值得做的，就說「這次沒有重大事件」，然後只 commit `tools/watch-state.json`。

## 第 3 步：取得原文

1. 把要引用的文件加進 `data/sources.json`：`{ id, publisher, title, url, asOf, type }`，`type` 是「官方」「研究機構」或「媒體」。
2. 下載原文成文字（SEC 申報的附件網址在 `inbox/new-items.json` 的 `exhibits`）：
   ```bash
   node tools/fetch-text.mjs <網址> <來源代號>
   ```
   存到 `sources/texts/<來源代號>.txt`。台積電新聞稿網站（pr.tsmc.com）會擋程式，改用 SEC 上的同一份附件。聯邦公報的網頁版也會擋，要用 `inbox/new-items.json` 裡的 PDF 附件網址（govinfo.gov）。PDF 會自動取文字（只適用文字型 PDF）。
   工具如果偵測到下載的是「擋機器人」的頁面，會拒絕存檔並顯示原因；**絕對不要**把那種頁面當成原文。
3. 想和歷史數字比（折線圖需要連續幾期）：用 `node tools/sec-fetch.cjs 代號 --form=6-K --since=日期 --list` 找過去幾期的官方文件，同樣下載成文字。**折線圖的每一個點都要有來源。**

## 第 4 步：寫事件

照 `data/events.json` 裡既有的事件寫成一個 JSON 檔，存到 `drafts/<事件代號>.json`（暫存的工作檔，不會上傳 GitHub）。格式見 `data/README.md` 的「events.json」。重點：

- `origin`：官方文件填「官方」；媒體或研究機構填「二手」（網站會顯示來源類型）。
- `status`：先寫「待審核」（上線時工具會自動改成「自動整理・待審核」）。
- `briefing`：4–8 張，**多用圖表**：`kpi` 重點數字、`line` 折線圖（趨勢，財測用虛線）、`dbars` 正負長條（成長率）、`segbar` 占比、`stat`／`story` 補充。資料不夠畫圖就不要硬畫。
- `matrix`：影響矩陣，3 個面向（需求面、獲利面、要觀察的變數），來源沒直接說的標 `infer: true`。
- `impacts`：受惠（+）、受壓（−）、影響不大（0），每個附原因。
- `questions`：剛好 3 題，至少 1 題看圖題（`visual`）；每題附解析和來源；錯誤選項要合理，不要明顯荒謬。
- `derived`：推算出來的數字。
- `conclusion`：一句話看局勢。

## 第 5 步：自動檢查

```bash
node tools/check-event.mjs --file=drafts/<事件代號>.json
```

結論有三種：

- **auto**（通過所有檢查）：可以上線。官方或二手來源都一樣。
- **reject**（有錯誤）：照訊息修；修不好的就放棄這個事件，不要硬上線。

## 第 6 步：上線（auto 才能上線，不需要等使用者確認）

```bash
node tools/check-event.mjs --file=drafts/<事件代號>.json --publish
```

工具會再檢查一次，通過才加進 `data/events.json`，狀態是「自動整理・待審核」，網站上會顯示 🤖 標籤，讓讀者知道這是自動整理的。
上線後要檢查畫面：用 `node tools/serve.mjs` 開網站，確認事件任務從頭到尾可以玩（簡報、地圖、矩陣、3 題）。

## 第 7 步：收尾

1. 在 `查證報告.md` 最後新增一節「YYYY-MM-DD 自動事件：事件標題」，列出：用了哪些來源、哪些數字是推算的、檢查結果。
2. Git commit，訊息：「自動事件：事件標題（來源名稱）」。要 commit 的有：`data/events.json`、`data/sources.json`、`tools/watch-state.json`、`查證報告.md`。**不要** commit `sources/`、`inbox/`、`drafts/`。
3. 通過檢查的事件，直接 commit 並 push 到 `main`，網站隨之更新（使用者已同意不用逐件確認）。**檢查沒過、修不好的事件就放棄**，不要硬上線，只在回報裡說明原因。
4. 本機手動執行時，commit 之後把結果簡短回報給使用者；雲端排程執行時，結果寫在排程的回報裡。

## 回報格式（最後給使用者的話）

- 檢查了哪些來源、找到幾份新文件
- 做了哪些事件（標題、來源、檢查結果）；放棄的事件和原因分開寫
- 跳過了哪些、為什麼
- 有沒有來源失敗（網站擋程式、改版）
